## 1. 목적
이메일 링크로 착지한 사용자가 **새 비밀번호를 입력해 계정 비밀번호를 재설정**하는 화면. 요청 화면(`/find-account`)에서 시작한 재설정 플로우의 마지막 단계다.

- 핵심 사용자: 비밀번호를 잊어 재설정 메일 링크로 들어온 회원.
- 성공 기준: 새 비밀번호 저장 완료 → 완료 안내 → 로그인 화면(홈) 복귀.

## 2. 권한
링크에 담긴 **1회용 재설정 토큰**을 가진 사람. 로그인/세션 불필요. 유효한 `token` 쿼리가 없으면 입력 폼이 아예 노출되지 않는다(§3.2). 토큰의 유효성·만료·사용여부는 백엔드가 검증한다(§3.3).

## 3. UI 블록 (위 → 아래)

화면은 중앙 카드 하나로 구성된다. 반응형: `<640px`는 흰 풀페이지, `≥640px(sm)`는 배경 위 카드(`470px`).

### 3.0 로고 + 타이틀
- **기능**: 상단 로고, "비밀번호 재설정" 타이틀 + "재설정할 비밀번호를 입력해 주세요" 안내 문구.
- **규칙**: 정적 표시. `token` 유무와 무관하게 항상 노출.

### 3.1 토큰 파싱 (진입 처리)
- **기능**: URL 쿼리 `?token=` 값을 읽어 이후 폼/에러 노출을 분기.
- **규칙**:
  - `useSearchParams()`로 `token`을 읽고, 없으면 빈 문자열(`""`)로 취급.
  - `useSearchParams` 사용을 위해 페이지는 **`<Suspense>` 경계**로 감싼다(Next 16 요구). fallback은 없음(`null`).
  - `token`이 있으면 → 입력 폼(§3.2), 없으면 → 무효 접근 안내(§3.2 대체 블록).

### 3.2 비밀번호 입력 폼 (token 있을 때)
- **기능**: 새 비밀번호 + 확인용 재입력 2개 필드 + 제출 버튼.
- **규칙**:
  - **비밀번호 입력**: `type="password"`. placeholder "비밀번호를 입력해 주세요".
  - **비밀번호 확인 입력**: `type="password"`. placeholder "비밀번호를 한번 더 입력해 주세요".
  - **클라이언트 검증(제출 시)**:
    - 둘 중 하나라도 비어 있으면 → `"비밀번호를 입력해 주세요."` 표시, 요청 안 보냄.
    - 두 값이 다르면 → `"비밀번호가 일치하지 않습니다."` 표시, 요청 안 보냄.
    - **길이/복잡도 검증은 클라이언트에 없음.** 최소 길이(8자)는 백엔드 스키마(`new_password: min_length=8`)에서만 강제 → 7자 이하 입력 시 서버 에러로 반환되어 §3.3 catch로 처리됨.
  - **에러 표시**: 필드 하단에 빨간 문구. 에러 상태에서 두 입력의 테두리/배경이 에러 스타일로 바뀜. 입력값을 다시 바꾸면 에러 문구는 초기화.
  - **제출 버튼**:
    - 라벨 "비밀번호 재설정", 요청 중에는 "재설정 중...".
    - **활성 조건**: 두 필드 모두 비어있지 않고 + 요청 대기중이 아닐 때. (일치 여부는 버튼 활성 조건이 아니며 제출 시 검증)
    - 클릭 → `confirmPasswordReset({ token, new_password })` 호출(백엔드 `POST /auth/password-reset/confirm`, payload key = `new_password`).
- `❓` 비밀번호 자릿수/복잡도 규칙(대소문자·숫자·특수문자)에 대한 **클라이언트 안내 문구 부재** — 8자 미만은 서버 에러 후 "만료/무효" 문구로만 안내됨(정확한 사유 미표시).

### 3.2-대체 무효 접근 안내 (token 없을 때)
- **기능**: 입력 폼 대신 노출되는 안내 문구.
- **규칙**: `token`이 없으면 폼을 감추고 `"유효하지 않은 접근입니다. 비밀번호 재설정 메일의 링크로 다시 접속해 주세요."`를 표시. 재요청 버튼/링크는 없음 ❓.

### 3.3 제출 결과 처리
- **기능**: confirm 요청의 성공/실패에 따른 분기.
- **규칙**:
  - **성공(204 No Content)** → 완료 모달(§3.4)을 연다.
  - **실패(any error)** → `"링크가 만료되었거나 유효하지 않습니다. 다시 요청해 주세요."` 문구를 폼 하단에 표시.
    - 프론트는 에러 종류를 구분하지 않고 **모든 실패를 이 한 문구로** 처리한다.
    - 백엔드 실패 사유(구분됨): 토큰 없음 / 이미 사용됨(`used`) / 만료(`expires_at < now`) → **400 "유효하지 않거나 만료된 토큰입니다."**. 8자 미만 비밀번호 → 422(스키마 검증). 모두 프론트에서는 동일 문구로 표시.
  - **서버 부수효과(성공 시)**: 해당 토큰을 `used=True`로 소진(1회용) + 그 사용자의 **모든 리프레시 토큰을 revoke**(기존 세션 무효화).

### 3.4 완료 모달
- **기능**: 재설정 성공 안내 다이얼로그.
- **규칙**:
  - 문구 `"비밀번호가 재설정 되었습니다."` + `"닫기"` 버튼.
  - **닫기** 클릭 → `router.replace("/")`로 홈(로그인 진입점)으로 이동. (뒤로가기로 이 화면에 되돌아오지 않도록 `replace`)
  - 모달 바깥 닫힘(`onOpenChange`)도 열림 상태만 토글하며 이동은 "닫기" 버튼에서 수행 ❓(오버레이/ESC 닫기 시 이동 없이 폼으로 남는 동작 의도 여부).

## 4. 화면 상태

| 상태 | 발생 조건 | 노출 / 동작 |
|---|---|---|
| 무효 접근 | `?token=` 없음 | 입력 폼 숨김 + "유효하지 않은 접근입니다…" 안내 (§3.2-대체) |
| 기본(입력) | `token` 있음 | 비밀번호 2필드 + 제출 버튼 (§3.2) |
| 검증 실패(클라) | 미입력 / 불일치 | 인라인 에러 문구, 요청 미발송 |
| 제출 중 | confirm 요청 대기 | 버튼 "재설정 중...", 버튼 비활성 |
| 실패(서버) | 토큰 무효·만료·사용됨 / 8자 미만 | "링크가 만료되었거나 유효하지 않습니다…" 인라인 에러 |
| 완료 | confirm 204 성공 | 완료 모달 → 닫기 시 홈 이동 |

## 5. 데이터 & 연동

| 항목 | 출처 / 연동 | 트리거 · 비고 |
|---|---|---|
| 재설정 토큰 | URL 쿼리 `?token=` | 진입 시 `useSearchParams`로 파싱. TTL **60분**(백엔드 `PASSWORD_RESET_TTL_SECONDS=3600`) |
| 비밀번호 재설정 확정 | `POST /auth/password-reset/confirm` (`useConfirmPasswordReset`) | 폼 제출 시. payload `{ token, new_password }`, 성공 204 |
| (선행) 재설정 요청/발송 | `POST /auth/password-reset/request` | `/find-account` 화면에서 발송. 링크 = `{email_link_base}/reset-password?token=…` |
