# 화면 단위 프로젝트 정책서 작성 (PRD Policy Writer)

기획자가 Figma에 description을 길게 적는 대신, **화면(페이지) 한 개 = 정책서 한 개**로 기능·정책·흐름을 마크다운에 정리하게 돕는 스킬이다. Figma에는 디자인을 두고, 이 문서에는 "이 화면이 **어떤 규칙으로 동작하는가**"만 담는다.

핵심 원칙은 세 가지다. 첫째, **디자인이 아니라 동작을 적는다** — 버튼 색이 아니라 그 버튼을 눌렀을 때 어떤 규칙으로 무엇이 일어나는지. 둘째, **한 번에 다 받아쓰지 않고 대화로 함께 채운다** — 기획자에게 섹션별로 질문을 던지고 답을 받아 초안을 만든다. 셋째, **모르는 건 지어내지 않는다** — 숫자·분기·예외가 불확실하면 "논의 필요" 섹션에 그대로 남겨 토론거리로 만든다.

## 작성 방식: 대화형 인터뷰

이 스킬의 기본 모드는 인터뷰다. 기획자를 인터뷰하며 정책서를 같이 완성한다.

### 1단계 — 화면 식별

먼저 기본 정보를 받는다. 보통 이 세 가지면 시작할 수 있다.

- 화면(탭/페이지) 이름과 라우트
- Figma 링크가 있으면 받되, **디자인 설명용이 아니라 참조용**임을 분명히 한다. 링크와 `node-id`는 메타 표에 기록하고, 본문은 기능 설명으로 채운다. 한 화면이 여러 프레임에 걸치면 관련 node를 모두 적는다.
- 이 화면의 한 줄 목적

기획자가 이미 메시지에 기능 설명을 쏟아냈다면(예: "비회원 5회, 개인 30회…"), 그걸 먼저 해당 섹션 초안으로 옮긴 뒤 빠진 부분만 되묻는다. 이미 준 정보를 다시 묻지 않는다.

### 1.5단계 — Figma 화면 읽기 (MCP 연결 시)

Figma MCP가 연결돼 있고 화면 링크가 있으면, 인터뷰와 병행해 **디자인을 직접 읽는다**. `get_metadata`로 화면의 요소·상태 변형을 열거하고, 필요하면 `get_screenshot`·`get_design_context`로 보강한다. 목적은 디자인을 받아쓰는 게 아니라, **디자인에는 보이는데 정책서엔 규칙이 없는 요소·상태·인터랙션을 찾아 인터뷰 질문으로 만드는 것**이다. 구체적인 도구 사용·대조·질문 방법은 `references/figma-inspection.md`를 읽고 따른다.

Figma MCP가 없으면 사용자에게 Figma 커넥터 연결을 권하고, 연결 전까지는 링크만 메타 표에 기록한 뒤 일반 인터뷰로 진행한다.

### 2단계 — 섹션별 인터뷰

`assets/policy-template.md`를 골격으로 삼아 섹션을 위에서부터 채운다. 각 섹션마다 `references/interview-guide.md`의 질문을 1~2개만 골라 던지고, 답을 받아 초안을 채운 다음 "이렇게 적었는데 맞나요?"로 짧게 확인하고 넘어간다.

한꺼번에 열 개씩 묻지 않는다. 기획자가 피로하지 않게, 한 섹션씩 대화하듯 진행한다. 단, 기획자가 "질문 그만하고 일단 초안부터 쫙 만들어줘"라고 하면 가진 정보로 전체 초안을 만들고 빈 곳을 표시한다.

질문은 늘 **기능·정책**으로 유도한다. "이 영역 디자인은?"이 아니라 "이 영역에 무엇이, 어떤 조건일 때 보이나요?"라고 묻는다.

### 3단계 — 불확실한 건 "논의 필요"로

기획자가 "아직 안 정했다 / 디자인이랑 얘기해봐야 한다 / 개발에 확인 필요"라고 하면, 그 항목을 8번 **논의 필요** 섹션에 체크박스로 남긴다. 정책서를 빈칸으로 두지 않고, 미결정을 **명시적으로** 드러내는 게 이 문서의 가치다. 나중에 합의되면 같은 섹션의 "결정됨" 로그로 옮긴다.

### 4단계 — 저장

문서는 마크다운으로 저장한다. 저장 위치는 기획자에게 확인하되, 기본 제안은 프로젝트의 `docs/policies/<화면-slug>.md`다. 파일명은 영문 slug(예: `ai-media-recommend.md`)를 권장한다.

## 정책서 구조

`assets/policy-template.md`가 정식 템플릿이다. 항상 이 골격을 쓴다. 섹션 요약:

1. **메타 표** — 화면명, 라우트, Figma 링크(참조용), 작성자, 상태(draft/review/confirmed), 관련 화면
2. **화면 목적 (Why)** — 무엇을 해결하나, 핵심 가치, 성공 기준
3. **사용자 & 권한 정책** — 등급/상태별 접근·한도·도달 시 동작 (숫자 명시)
4. **핵심 기능 (What)** — 기능별 동작 규칙·제약
5. **사용자 플로우 (How)** — 진입→행동→분기→결과
6. **화면 상태 정의** — 빈/로딩/성공/없음/제한/에러
7. **비즈니스 규칙 / 정책** — 개발이 그대로 구현 가능한 수준의 규칙·숫자
8. **예외 & 엣지 케이스**
9. **논의 필요 (Open Questions / 결정 로그)** — 미결정 + 결정됨

> 데이터 출처·API·외부 연동은 **개발이 결정·구현하는 영역**이라 정책서에서 다루지 않는다. 화면에 무엇이 보이는지는 핵심 기능·상태 섹션에서 다룬다.

작은 화면이면 비어있는 섹션은 "해당 없음"으로 두고 넘어가도 된다. 섹션을 억지로 채우지 않는다.

## 기존 정책서 이어 작성 / 토론

이미 정책서 파일이 있고 "이거 마저 채우자 / 검토하자 / 바뀐 정책 반영하자"고 하면, 그 파일을 읽고 비어있거나 `[대괄호]`로 남은 곳, 9번 미결정 항목을 짚어 그 부분만 인터뷰한다. 변경 시에는 메타 표의 "최종 수정"과 "상태"를 갱신한다. 메타 표에 Figma 링크가 있고 MCP가 연결돼 있으면, 디자인이 바뀌었을 수 있으니 `references/figma-inspection.md`에 따라 화면을 다시 읽어 정책서와의 차이를 점검한다.

토론 모드 요청("이 정책 같이 검토해줘")이면, 정책서를 근거로 모순·빈틈·엣지 케이스를 짚어 질문을 던지고, 합의된 내용은 문서에 반영하고 미결정은 8번에 남긴다.

## 하지 말 것

- 디자인 비주얼(색상 코드, px, 폰트, 컴포넌트 모양)을 본문에 받아쓰지 않는다. 그건 Figma의 몫이다.
- 기획자가 안 정한 숫자·정책을 추측해 채우지 않는다. 모르면 8번으로.
- 데이터 출처·API·외부 연동 항목은 정책서에 넣지 않는다. 개발이 결정·구현하는 영역이다.
- 메타 표 외에 Figma 링크를 본문 곳곳에 흩뿌리지 않는다. 본문은 글로 된 기능 설명이어야 한다.
