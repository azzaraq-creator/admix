# Figma 화면 분석 → 빈틈 인터뷰

Figma MCP가 연결돼 있고 화면의 Figma 링크가 있으면, **디자인을 직접 읽어 정책서가 다루지 않은 부분을 찾아 인터뷰**한다. 디자인을 받아쓰는 게 아니라, 디자인을 단서로 "여기 보이는 이건 어떤 규칙으로 동작하나요?"를 묻는 게 목적이다.

## 0. 연결 확인

Figma MCP 도구(예: `get_metadata`, `get_screenshot`, `get_design_context`)가 사용 가능한지 본다. 없으면 사용자에게 Figma 커넥터 연결을 권하고, 연결 전까지는 일반 인터뷰로 진행한다. 도구 이름 앞부분(prefix)은 연결 방식에 따라 다를 수 있으니, 실제 사용 가능한 Figma 관련 도구를 쓴다.

## 1. 노드 지정

기획자가 준 Figma URL에서 `node-id`를 확보한다. (URL의 `node-id=759-99870` 형태. 콜론/하이픈 표기는 도구 요구에 맞춰 변환.) 한 화면이 여러 프레임에 걸쳐 있으면 관련 node 들을 모두 메타 표에 기록한다.

## 2. 화면 읽기

도구를 조합해 화면을 파악한다. 한 번에 다 부르지 말고 필요한 만큼.

- **`get_metadata`** — 해당 node의 레이어/프레임 구조(이름·타입·계층). 화면에 어떤 요소(버튼, 입력창, 리스트, 탭, 모달 등)가 있는지 **열거**하는 데 쓴다. 인터뷰의 출발점.
- **`get_screenshot`** — 화면 이미지. 구조만으로 안 잡히는 배치·맥락을 눈으로 확인.
- **`get_design_context`** (또는 코드/텍스트 컨텍스트 도구) — 실제 텍스트 문구, 상태 변형(variant), 컴포넌트 속성. 빈 상태/에러/뱃지/카운터 같은 **상태 변형**을 찾는 데 특히 유용.
- **`get_variable_defs`** — 필요 시 한도 수치 등이 변수로 들어가 있는지 확인(예: 토큰 카운트). 보통은 생략 가능.

읽은 내용 중 **디자인 속성(색·px·폰트)** 은 정책서에 옮기지 않는다. 우리가 추출하는 건 "어떤 기능 요소·상태·분기가 존재하는가"뿐이다.

## 3. 정책서와 대조 → 빈틈 찾기

화면에서 관찰한 요소·상태·인터랙션을, 작성 중인(또는 작성된) 정책서와 맞춰 본다. 다음을 빈틈으로 본다.

- 디자인엔 있는데 정책서 **3번 핵심 기능**에 없는 버튼/액션 → "이 ◯◯ 버튼은 어떤 규칙으로 동작하나요?"
- 디자인에 보이는 **상태 변형**(빈 상태, 로딩, 에러, 뱃지, 비활성, 카운터 등)이 **5번 상태 정의**에 없음 → "이 상태는 언제 뜨고 뭐가 달라지나요?"
- 모달/토스트/툴팁/배너 같은 보조 UI가 정책서에 언급 없음 → "이건 어떤 조건에서 뜨나요?"
- 화면 안의 숫자·뱃지·카운트(예: 잔여 횟수 표시)에 대한 **계산/표기 규칙**이 6번에 없음.
- 다른 화면으로 가는 진입점(링크/CTA)이 4번 플로우에 빠짐 → "이걸 누르면 어디로, 어떤 조건에서 가나요?"
- 입력 폼이 보이면 검증 규칙·필수 여부가 정책서에 없음.

## 4. 인터뷰

찾은 빈틈을 **한 번에 쏟지 말고** 묶어서 3~5개씩, 디자인 근거와 함께 묻는다.

> "Figma 화면을 보니 추천 리스트 카드에 '관심 매체' 아이콘과 잔여 횟수 뱃지가 있는데, 지금 정책서엔 규칙이 없어요. ① 관심 매체 토글은 비회원도 되나요? ② 뱃지의 숫자는 무엇을 세나요?"

기획자 답은 해당 섹션에 반영하고, 안 정해진 건 8번 **논의 필요**에 남긴다. 디자인에서 봤지만 기획자도 모르는 요소는 "Figma엔 있으나 정책 미정"으로 8번에 적어 디자인·개발과의 토론거리로 만든다.

## 5. 기록

확인한 모든 관련 node 링크를 정책서 메타 표 "Figma (참조용)"에 적어, 나중에 같은 화면을 다시 열 때 추적 가능하게 한다. 화면이 바뀌면(디자인 업데이트) 다시 2~4단계를 돌려 정책서와의 차이를 점검한다.

## 주의

- Figma는 **단서**일 뿐 정답이 아니다. 디자인에 있다고 정책으로 단정하지 말고 반드시 기획자에게 확인한다.
- 디자인에 없지만 정책상 필요한 상태(예: 에러 처리)는 디자인 누락일 수 있으니 그것도 빈틈으로 짚는다 — 정책서는 디자인보다 넓을 수 있다.
